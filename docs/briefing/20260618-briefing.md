# Project Briefing: EccoVox

**Data**: 2026-06-18
**Status**: Draft
**Versão**: 1.0

---

## 1. Visão e Propósito

**O que é**: EccoVox é um runtime local independente para capacidades de voz, incubado dentro do monorepo atual, mas tratado como projeto separado. [fornecido]

**Problema que resolve**: O projeto cria uma borda estável para transcrição de fala em texto e síntese de texto em áudio, evitando que aplicações consumidoras integrem diretamente bibliotecas Python específicas. [inferido]

**Proposta de valor**: Consumidores podem usar EccoVox como serviço HTTP persistente ou como executável sob demanda, mantendo isolamento de engines, configuração e contrato de voz. [fornecido/inferido]

## 2. Usuários e Stakeholders

| Ator | Papel | Ações Principais |
|------|-------|------------------|
| Aplicação consumidora | Cliente de API/CLI | Solicita transcrição STT e síntese TTS sem conhecer engines internas. |
| Operador de deploy | Responsável por runtime | Instala dependências, configura modelos, inicia servidor ou executa CLI. |
| Desenvolvedor integrador | Consumidor técnico | Integra endpoints HTTP ou comandos CLI em uma aplicação externa. |
| Rodrigo | Decisor do projeto | Define prioridades, valida arquitetura e documentação. |

**Stakeholders de decisão**: Rodrigo é o decisor identificado. [fornecido]

## 3. Escopo

### MVP (Essencial)

1. Criar estrutura inicial do projeto Python independente dentro de `modules/eccovox`. [fornecido]
2. Documentar o projeto com briefing e constitution próprios. [fornecido]
3. Definir API HTTP para STT e TTS. [fornecido]
4. Definir CLI/executável para STT e TTS sob demanda. [fornecido]
5. Manter EccoVox sem conhecimento de Jarvis, AIChat ou qualquer host específico. [fornecido]
6. Preparar arquitetura para usar Whisper/faster-whisper no STT e Kokoro no TTS. [fornecido]

### Pós-MVP (Desejável)

1. Suporte a conversação live ou streaming de voz. [fornecido]
2. Suporte a múltiplas engines por capacidade. [inferido]
3. Perfis de qualidade e performance por ambiente. [inferido]
4. Empacotamento para execução como serviço do sistema. [inferido]
5. Observabilidade avançada e métricas operacionais. [inferido]

### Fora de Escopo

- Implementar conversação live na primeira fase.
- Conhecer regras, usuários, roles ou domínio do Jarvis.
- Persistir histórico conversacional.
- Substituir a aplicação consumidora; EccoVox é runtime de voz, não assistente.

## 4. Prioridades e Trade-offs

**Ordem de prioridade**: Independência do projeto > contrato estável > execução HTTP e CLI > qualidade de voz > extensibilidade futura. [inferido]

**Decisões explícitas**:
- O projeto se chama EccoVox, escrito com dois `c`. [fornecido]
- EccoVox fica incubado no repositório atual como submódulo/pasta de projeto, mas deve ser tratado como produto independente. [fornecido]
- EccoVox deve poder rodar como servidor de API e como executável para conversões pontuais. [fornecido]
- O escopo inicial cobre apenas STT e TTS. [fornecido]
- Conversação live deve ser considerada na arquitetura, mas não implementada na primeira fase. [fornecido]

## 6. Stack Técnica

| Camada | Tecnologia | Justificativa |
|--------|------------|---------------|
| Runtime | Python | As engines alvo são bibliotecas Python. [inferido] |
| STT | Whisper/faster-whisper | Motor alvo para transcrição. [fornecido] |
| TTS | Kokoro | Motor alvo para síntese de voz. [fornecido] |
| API | HTTP | Contrato estável para consumidores externos. [fornecido] |
| CLI | Executável `eccovox` | Execução sob demanda sem servidor persistente. [fornecido] |
| Deploy | Processo local ou serviço do SO | Permite modo persistente e modo pontual. [inferido] |

## 7. Qualidade e Padrões

**Padrões adotados**:
- Contratos HTTP e CLI devem ser documentados antes da implementação. [inferido]
- O runtime deve isolar engines concretas atrás de interfaces internas. [inferido]
- Erros devem ser funcionais e estáveis para consumidores. [inferido]
- Logs não devem expor áudio bruto, texto sensível integral ou segredos. [inferido]
- A arquitetura deve permitir expansão futura para live/streaming sem reescrever o contrato básico de STT/TTS. [fornecido/inferido]

**Compliance**: Não definido.

## 8. Visão de Futuro

**6 meses**: EccoVox deve oferecer API e CLI estáveis para STT/TTS local, com documentação suficiente para ser consumido por Jarvis ou qualquer outro host. [inferido]

**12 meses**: EccoVox pode evoluir para streaming de voz, conversação live, múltiplas engines, empacotamento independente e telemetria operacional. [fornecido/inferido]

**Riscos conhecidos**:
- Carregamento de modelos pode tornar CLI sob demanda lento para uso conversacional. [inferido]
- Servidor persistente melhora latência, mas consome memória mesmo ocioso. [inferido]
- APIs acopladas demais a uma engine dificultam troca futura de Whisper/Kokoro. [inferido]
- Sem limites de concorrência, múltiplas chamadas podem esgotar CPU, RAM ou VRAM. [inferido]
